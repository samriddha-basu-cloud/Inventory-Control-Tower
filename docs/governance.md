# Governance

## Reversible autonomy matrix (section 81)

`Recommendation.autonomy_level` encodes the levels described in the brief:

- **0 — Observe**: not currently used (every alert becomes an observable
  record; nothing is hidden).
- **1 — Recommend** (default for everything the platform generates today):
  shown in the Recommendations queue, requires a human decision.
- **2 — Recommend + approval**: identical mechanically to level 1 in this
  build (both stop at "approved, awaiting execution").
- **3 — Auto-execute within guardrails**: implemented as a threshold check
  in `app/routes/alerts.py::decide_recommendation` — a recommendation with
  `autonomy_level >= 3` and `cost_estimate <= 50,000` auto-executes
  (simulated) on approval; everything else waits for the separate Execute
  step. **No recommendation generated by this build is created with
  autonomy_level 3** — the demo data and services all create recommendations
  at level 1, so nothing auto-executes today. The guardrail code exists and
  is exercised by the workflow, but level-3 recommendations would need to be
  deliberately created (e.g. via the API) to see it fire.
- **4 — Conditional autonomous execution**: not implemented.

## Execution safety (section 147)

Before a simulated execution runs, `execute_recommendation` re-checks source
availability against the recommendation's quantity and **blocks** execution
with a stated reason if availability has fallen since approval (see
`app/routes/alerts.py`). This is validated in
`tests/test_integration_demo.py::test_recommendation_approval_workflow`
indirectly (the approve→execute path); the blocked path is covered by the
`blocked_reason` logic but does not currently have a dedicated failing-case
test - a good addition for the next test pass.

## Audit trail

`Approval` records who decided what and why, with a timestamp.  `Execution`
records the mode (always `SIMULATED` in this build - see
`known-limitations.md`), result, and detail. `AuditLog` exists in the schema
for broader data/policy-change tracking but is not yet written to by every
mutation path - only approvals/executions are guaranteed to be recorded
today via their dedicated tables.

## Human override (section 143)

`SafetyStockPolicy.override_safety_stock` / `.override_reason` /
`.override_by` exist in the schema so a planner's manual safety-stock
override is tracked separately from the system-calculated value
(`effective_safety_stock` prefers the override when set). There is currently
no UI form to set an override - it must be set via the API/DB directly. This
is called out explicitly rather than silently left half-built.
